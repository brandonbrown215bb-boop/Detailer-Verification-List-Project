# 1. AHU Detailing Verification Desktop Application Architecture

Date: 2026-08-24
Status: Accepted

## Context

AHU detailing verification requires validating complex engineering configurations (`Config.xml` generated by selection software) against extensive fabrication and engineering rules, managing Special Quotes (SQs), and generating an official `Detailing Verification List.xlsx` workbook for checkers. Previously, this was a manual process prone to missed checks and Excel formula/validation corruption.

## Decisions

1. **Technology Stack**: .NET 8 / C# Windows desktop application hosting Microsoft Edge WebView2, with an embedded Vite + TypeScript frontend communicating via a typed asynchronous message bridge.
2. **Excel Engine**: `DocumentFormat.OpenXml` (v3.1.1+) strictly used for template patching, preserving all 12 `DataValidations` elements and all 23 formula chains on `Check Information`.
3. **Rule Pack Foundation & Transcription Policy**:
   - Rule extraction from the 12-sheet Excel template is strict transcription, not speculative interpretation.
   - Stable semantic IDs, categories, and scopes (`Unit`, `Skid`, `Segment`, `Component`).
   - JSON-AST predicates are only encoded where triggers are backed by confirmed engineering logic; ambiguous items evaluate to `Needs Input` / require explicit confirmation.
   - Decoupled physical cell addresses via `template_map.json`.
4. **Two-Layer Data Architecture**:
   - Layer 1 (`NormalizedXmlGraph`): Structural, uninterpreted representation of `Config.xml`.
   - Layer 2 (`FactRegistry`): 4-state provenance-aware facts (`Known`, `Derived`, `Unknown`, `ManuallyOverridden`) with confidence tracking (`Authoritative`, `RequiresConfirmation`).
   - Automatic immediate extraction upon XML file drop/load.
5. **UI & Navigation Structure**:
   - Skid-centric tabbed views: 'General Unit' tab for global unit specs, SQs, and unit-level rules, followed by dynamic tabs for each Shipping Skid ('Skid 1', 'Skid 2', etc.) containing that skid's scoped component rules (Base, Segments, Internals, Reconnects).
6. **Project Persistence (`.dvl`)**:
   - Fully self-contained `.dvl` JSON format embedding the raw `Config.xml` and pinned Rule Pack hash.
   - Continuous background autosaving to `%LOCALAPPDATA%/AHUVerification/autosave.dvl` for crash recovery.
7. **Special Quotes (SQs) Management**:
   - Dynamic SQ manager supporting item numbering, descriptions, and optional cross-linking to skids/rules, mapped to the official 22-slot table on `Verification List`.
8. **Export Validation & Gating**:
   - Pre-flight modal dialog upon export with Draft mode (watermarked/warned) vs Final Verification Deliverable mode (requires resolving all pending items).
9. **Rule Pack Distribution & Offline Resilience**:
   - Embedded baseline Rule Pack v1.0.0 for zero-config offline start, plus configurable remote sync (OneDrive/SharePoint/UNC) with SHA-256 integrity verification and Last Known Good (LKG) rollback.

## Consequences

- High developer velocity and modularity by cleanly separating rule logic from Excel cell coordinates.
- Complete fidelity to existing engineering standards without risking Excel corruption.
- Robust offline operation on detailer workstations without network dependencies.

## Addendum (2026-08-26)

1. **Framework & Packaging Correction**: The current projects target **.NET 8** (`net8.0-windows` / `net8.0`), not .NET 10. Delivery remains folder-based (`PublishSingleFile=false`) with adjacent `dist/`, `resources/rulepack/`, and `resources/bin/` directories.
2. **Dynamic OpenXML Deliverable Synthesis**: Decision 2 is superseded by ADR-0005. Inactive category worksheets are pruned, formula chains on `Check Information` are adapted dynamically to eliminate `#REF!` errors, `CalculationChainPart` is dropped to force Excel recalculation, and `Verification List` rows ($\ge 26$) are built dynamically grouped by shipping skid sections.
3. **Client Storage & Autosave**: Frontend debounces active state autosaves to WebView2 `localStorage` (`ahu_dvl_autosave`), while `%LOCALAPPDATA%/AHUVerification/WebView2Data/` provides isolated runtime profile storage.
   This is crash-recovery state, not an atomic `.dvl` file write. If it is unavailable or malformed, the user must reopen/import the source or a saved `.dvl`; no automatic file-level recovery is implemented here.
